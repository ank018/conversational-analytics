Project 02 · Text-to-SQL over a real warehouse

Conversational Analytics

Ask a Brazilian e-commerce warehouse a question in English and get an answer. The interesting question is not whether it answers — it always answers — but how often the answer is right, and how you would ever know.

Noise floor 2.7 points. Four runs of a byte-identical prompt at
    temperature zero spanned 2.7 percentage points. Any delta smaller than that has not
    been demonstrated. The documented-schema row ran twice rather than three times, with
    dropped calls to provider rate limits; its prompts are 5.7× the baseline and it was
    the slowest configuration in the project. The schema-plus-rules interaction was not
    measured, so the negative result covers a bare prompt only.

  






  
Findings

  

    

      
01

      
Most wrong answers look right

      48.9% → 12.4%
      
Of 75 questions, one failed visibly. Thirty-seven returned a clean, plausible,
      incorrect number. Execution accuracy alone hides this; it is the figure a business
      should actually care about, and it is almost never reported.

    

    

      
02

      
One page of definitions was worth 36 points

      +36.0 pts
      
What revenue means, which orders count as sales, what a customer is, which of five
      date columns is “delivery”. A single rule — exclude cancelled and unavailable orders —
      accounted for 24 of the 27 recovered questions.

    

    

      
03

      
Documenting the schema did nothing

      −1.4 pts, 5.7× cost
      
Foreign keys, sample values, ranges, null counts, written notes on every ambiguous
      column. No measurable change, materially slower, more rate-limited. This is the fix
      most teams reach for first.

    

    

      
04

      
Retry loops had nothing to fix

      0 of 225
      
Repair can only trigger on a query that errors or returns nothing. Across 225
      question-runs with the rules in place, no query did either. Wrongness was semantic,
      and semantics leave no trace at execution time.

    

    

      
05

      
A single run is not a measurement

      ± 2.7 pts
      
Four runs of an identical prompt at temperature zero spanned 2.7 points, with five
      questions flipping between runs. Published figures quoted to one decimal from a single
      run report more precision than they have.

    

    

      
06

      
The diagnosis predicted the fix

      +37.3 predicted
      
Thirty-seven failed queries were hand-classified into causes before any fix was
      built. That taxonomy predicted the business rules would recover 37.3 points. Measured:
      36.0.

    

  






  
Method

  

    

      
How it was measured

      
    
        
  1. 86 questions written by hand, each with verified SQL and a human sign-off.
        Seventy-five answerable; eleven with no correct answer at all.
    2. 
        
  2. The evaluator was built before the system and tested in both directions —
        26 cases proving it accepts cosmetically different queries and catches the specific
        wrong ones.
    3. 
        
  3. Failures were classified by hand into named causes, producing a prediction
        for each intervention before any of them were built.
    4. 
        
  4. The noise floor was measured by running an identical prompt four times, so
        every later delta could be judged against it.
    5. 
      

    

    

      
Known limits

      
    
        
  • Follow-up questions work by resending the conversation. Not evaluated —
        the figures here are for single questions.
    • 
        
  • Eleven of 86 questions have no correct answer. Abstention was correct 7 of 11
        times, but that metric swung by three questions across identical runs and is too
        noisy to state precisely.
    • 
        
  • Two questions regressed when the rules were added: the model applied the status
        exclusion to payment-row counts the rules explicitly exempt. Stating an exception
        does not stop a model generalising past it.
    • 
        
  • Gold SQL is DuckDB-flavoured. The method transfers; these particular queries
        would need porting.
